Chapter 02

Lexical Structure

Lexical structure = the most basic writing rules of a language — how names are written, and how JavaScript knows where one statement ends and the next one begins.

Most of this chapter is common sense. The part that really matters is 2.6 Optional Semicolons — it's a well-known interview trap.

2.1 The Text of a JavaScript Program

  • Case-sensitive — capital and small letters are treated as different. So count and Count are two separate variables, and you must write while, never While.
  • Spaces and line breaks are ignored — you can add as many as you like to make code readable; JavaScript doesn't care. (There's one exception where a line break does matter — see 2.6.)

2.2 Comments

Nothing new — // for one line, /* ... */ for many lines.

2.3 Literals

  • A literal is a value you type directly into the code, like 42, "hello" or true. The word comes up often, so it's worth knowing.

2.4 Identifiers and Reserved Words

  • An identifier is simply a name — the name you give to a variable, function, class or object property. In let age = 25, age is the identifier.
  • Naming rule: a name must start with a letter, _ or $. Digits are allowed after that, but not first — user1 works, 1user doesn't.
  • Why no digit first? So JavaScript can tell straight away whether it's looking at a name or a number.
  • Reserved words are words JavaScript already uses for itself — if, for, class, return and so on. You can't use them as variable or function names. (They are allowed as object property names, like obj.class.)

2.5 Unicode

  • Unicode is a big list that gives every character in the world its own number — English letters, Hindi, Chinese, even emoji. Computers only store numbers, so this list is how they know which number means which character.
  • JavaScript code is written in Unicode, so strings can hold any language or emoji — "नमस्ते 😀" works fine.

2.6 Optional Semicolons

  • A statement is one complete instruction, like let x = 5. A semicolon ; marks where a statement ends.
  • In JavaScript you can usually leave the semicolon out if each statement is on its own line — JavaScript adds it for you.

This feature is called ASI (Automatic Semicolon Insertion). The important part is how it decides: at each line break, JavaScript checks whether the next line could carry on the current statement. If it can, JavaScript joins the lines. It adds a semicolon only when joining would make no sense.

How ASI reads code

let n
n
=
5
console.log(n)
  • let n then n → let n n makes no sense, so a semicolon is added.
  • n then = → n = can carry on, so the lines are joined. (n on its own would be fine too, but JavaScript always prefers to keep going.)
  • n = then 5 → n = 5, joined.
  • 5 then console → makes no sense, so a semicolon is added.

So JavaScript actually runs:

let n; n = 5; console.log(n);

Lesson: a line break is not the same as a semicolon. That's where the two traps below come from.

Trap 1: a line that starts with ( or [

JavaScript thinks this line is a continuation of the line above, and joins them:

let total = price + getTax
(a + b).toString()

This is read as getTax(a + b) — the function gets called by accident. Fix: end the first line with a semicolon.

Trap 2: a line break right after return

This one is the opposite — JavaScript always ends the statement right after return if a line break follows:

function getUser() {
  return
  { name: "Sourabh" };
}
getUser();
undefined

JavaScript reads it as return; — so the function returns nothing. Fix: start the value on the same line as return. (Same rule for break, continue and throw.)

Interview: "Are semicolons optional in JavaScript?" — Mostly yes, because of ASI. But ASI only adds a semicolon when the next line can't continue the statement. So a line starting with ( or [ gets joined to the line above, and a line break after return makes the function return undefined. The safe habit is to always write semicolons, or let a formatter like Prettier add them.

2.7 Summary

Only 2.6 is worth revising before an interview. The next chapter is where the real language starts — types and values.
